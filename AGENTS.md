# AGENTS.md

Aayatun: Flask + Jinja Quran web app. No build step, no bundler, no linter/formatter config, no automated tests, no CI. Frontend is server-rendered templates plus CDN jQuery/Fomantic and `static/`.

## Run & verify

- Run from the repo root; all data paths are relative (`db/…`, `db2/…`).
- `flask --app app.py run --debug` (or `python3 -m flask --app app.py run`; see `run_command.md`). `app.py` has no `__main__`, so `python3 app.py` silently does nothing.
- Dependencies: `pip install -r requirements.txt`. Docs target Python 3.10; the local `venv/` is an ignored, empty Python 3.13 skeleton (pip only). Use a fresh 3.10 venv or a Python that already has the deps (`python3` here does).
- `db2/quran_metadata.db` is Git LFS (~311 MB). Without `git lfs pull` verse pages fail.
- No test suite. Smoke-check a route with the real stack (allow a few seconds for outbound calls):
  `python3 -c "import app; print(app.app.test_client().get('/2/255').status_code)"`

## Data layout (directory names are misleading)

- `db/` — live SQLite DBs and JSON/text indexes (`quran.db`, translation/tafsir DBs, `ai_context.db`, `page_overviews.db`, `surah_overviews.db`, `ayah_themes.db`, `quran_stat.json`, `quran_index.txt`, `ruku_index.txt`, `sarf.json`).
- `db/qcf_verses.json` — **tracked** seed of all 6,236 verses as `{"verses": [[surah, verse, mushaf_page, code_v2], …]}`, generated once from quran.com's `by_page` endpoints with the page column corrected to the **V2** (`v2_page`) Madani page used by the QPC2 fonts. It is the source of truth for QCF text and mushaf-page membership; `_qcf_load_cache` seeds the in-process dict from it (the sqlite cache is only a fallback). Page membership follows V2, not the per-verse `page_number`/V1 page (5:77 says 121 but belongs to V2 page 120). `qcf_page_index` and `library.get_mushaf_page(page)` derive from it. The 56 V1/V2 mismatches were fixed when the layout mode was added.
- `db/mushaf_lines.json` — **tracked** line layout for the optional mushaf view: `{"pages": {"604": [["h", 112], ["b"], ["x", [[112, 1, "glyphs", "plain text"], …]], …]}}` for all 604 V2 pages (1.9 MB). Generated from [zonetecde/mushaf-layout](https://github.com/zonetecde/mushaf-layout) `v2/mushaf/QPC2/page-XXX.json`; the glyphs are the same QPC V2 set as `code_v2`, so `/font/v4/<page>.woff2` renders them, and the fourth element is that fragment's plain Uthmani text (upstream `words[].word`, grouped by verse) for the normal-font view. `library.get_mushaf_lines(page)` lazy-loads it once; keep it in sync with `qcf_verses.json` page membership if either is regenerated. Upstream puts a surah's banner as the **last** line of the previous page when the surah starts at the top of a page (18 cases, e.g. ‘Abasa on 584/585); `_mushaf_fix_banners()` moves it above the next page's basmala on load, so no page ends with a dangling banner and the JSON can be regenerated as-is.
- The `.txt` indexes (`quran_index.txt`, `ruku_index.txt`, `pos_tags_dict.txt`) are Python literals read with `eval`, not JSON; keep them valid Python when regenerating.
- `ai_context.db.verse_analysis.verse` is **0-based** (0 = ayah 1), unlike every other table; `library.RootDefAdder` applies the `verse - 1` shift.
- `db/page_overviews.db` — **tracked** SQLite table `page_overviews(page, context, summary, model, generated_at)`, one row per printed Madani page. `context` explains why the passage sits at that point in the surah's flow, `summary` says what the page discusses. Generated offline by `/mnt/d/PROJECTS/aayatun_ai_content/generate_page_overviews.py` (Gemini/OpenAI, batched and resumable); `library.get_page_overview(page)` reads it with `lru_cache` and returns `None` for missing rows, so partial generation only hides the accordion. The generator must run from the app root (all data paths are relative) and never stores the API key.
- `db/surah_overviews.db` — **tracked** SQLite table `surah_overviews(surah, context, summary, model, generated_at)`, one row per surah (1–114), same fields and privacy rules as the page overviews. `context` explains the surah's place in the mushaf and the concern that ties it together, `summary` follows the surah as a whole. Generated offline by `/mnt/d/PROJECTS/aayatun_ai_content/generate_surah_overviews.py` (OpenAI/Gemini, batched by verse count and resumable); `library.get_surah_overview(surah)` reads it with `lru_cache` and returns `None` for missing rows. The shared `comprehensive.html` renders `partials/_surah_overview.html` above the options block on every surah-wide page (`/translation`, `/tafsir/en`, `/tafsir/bn`, `/mushaf`), reusing the page-overview accordion styles and the AI notice.
- `db/ayah_themes.db` — **tracked** SQLite tables `themes(id, name, color)` and `verse_themes(surah, verse, theme_id)`, assigning one of 12 one-word themes to every ayah. Generated offline by `generate_ayah_themes.py` (OpenAI gpt-4o, batched and resumable; never stores the API key). `library.get_ayah_themes()` reads it with `lru_cache` and returns `{themes, verses}` where `verses` is a 6,236-entry canonical-order id array; the index route inlines it as `window.AAYATUN_THEMES`. The map popup's **Themes** switch fills every square with its theme and puts a white tick on every read verse (state ≥ 1); the visited-green page/frequency legend is replaced by a simplified one (`Unread` + `Read` with a ticked swatch) preceded by the context label `Verse Read Statistics:` between the switch and the legend. The selectable theme legend (sorted by frequency) highlights one theme at a time. The switch position is remembered in `localStorage['aayatun_read_map_themes_v1']`, and the popup carries the line `Verse themes: AI-assisted (Aayatun)`. The hover/selection readout shows the verse's theme (coloured chip + name) ahead of `Surah n:v — state`. Theme mode swaps every square with the site loading bar and a simple fade (no per-cell color transitions); motion respects `prefers-reduced-motion`. The verse detail page renders the same theme as a small pill at the left edge of the control row (`window.AAYATUN_SURAH_THEMES`, updated on `aayatun:verse`), which links to the `/theme/<id>` page for that theme (`?v=<surah>:<verse>` so the pill's verse is highlighted there; inside the modal iframe it navigates the parent). The share card gains a `theme` kind (first five verses, count, `Theme: <name>` title).
- `db2/quran_metadata.db` — per-verse pickled dicts used by every verse page (`library.get_verse_pickle`). Git LFS.
- `db/search.db` (~124 MB) — gitignored FTS5 index powering `/search`, built by `build_search.py` from local DBs (Arabic `db/quran.db`, English translation `db/en_quran.db`, EN/BN tafsirs, AI context flattened from `db/ai_context.db`). Run `python3 build_search.py` after any of those DBs change; `searchtool._ensure_db()` also builds it automatically on first search if the file is missing. Matching is done on a normalized form of every column (diacritics stripped, alif/hamza/ya/ta-marbuta unified, Bengali nukta decomposed) — see `searchnorm.py` — while display keeps the original text with matches highlighted via an index map; all columns are stored normalized with the raw text as `UNINDEXED` display columns. A `docs_trgm` trigram table over the Arabic and English text is the substring/root-search fallback; it is skipped automatically on hosts whose SQLite lacks the trigram tokenizer (needs SQLite ≥ 3.34, e.g. PythonAnywhere), where keyword search is otherwise unchanged — only substring fallback is lost. Ranking is BM25 (ar/en 10, AI 1.5, tafsirs 2, surah name 3) with per-column OR'ed clauses because plain FTS5 unfiltered matches flatten the column weights. Multi-word queries run an all-tokens pass first and merge those rows in front of the OR pass (bm25 within each tier), so complete matches always outrank partial matches; a trailing `*` is a prefix wildcard. `db/search_vocab.pkl` (token → frequency) powers edit-distance "did you mean" suggestions (BK-tree built lazily on the zero-hit path). `db/search_synonyms.json` holds curated synonym groups (English Quranic/transliteration terms + a small Arabic set); a glossary hit ORs the group into the query. `/search` also redirects `^\d+[:/.-]\d+$` (e.g. `2:255`) straight to the verse. The old Whoosh index (`db3/`) and `pd_backup.json` path are gone.
- `db/fonts/`, `db/qcf_cache.db`, `db/tajweed_cache.db` — gitignored runtime caches, safe to delete; they refetch on demand.
- The non-pickle code path is legacy: `getSurahInfo`, `get_morph`, `get_word_for_word_meaning` read `db/corpus.db`, `db/words.db`, `db/all_word_def.json`, none of which exist. Verse routes use `p_getSurahInfo()`.
- SQL is assembled with f-strings; route params are ints, but use bound parameters for any new string input.

## Architecture

- `app.py` holds all routes (flat, no blueprints). `/<surah>/<verse>` renders `versedetails.html` from `library.get_verse_core` (not `p_getSurahInfo`); `/search` is POST-only (form field `query_str`) and queries the FTS5 index. `/page/<n>` (1–604, prev/next wrap) renders one Madani mushaf page as a row-per-verse table grouped by surah (`templates/mushaf_page.html` + `library.get_mushaf_page`), with QCF text from the local seed. A third toggle, **Mushaf layout**, hides the table and the translation toggle and shows `library.get_mushaf_lines(page)` as printed lines (surah banner, Amiri basmala, glyph lines split into clickable verse segments that open the details modal); it is the default view, persisted in `localStorage['aayatun_mushaf_layout_v1']` where only an explicit `0` switches back to the table (a head script hides the table before first paint so it never flashes). The tajweed button stays in this mode: off shows the same line breaks in plain Uthmani text (Scheherazade) instead of the QCF glyphs, re-fitting the line size on each toggle. That plain text ends each verse's Arabic-Indic number in parentheses (`(٢٥٥)`), done in `get_mushaf_lines`, not stored in the JSON. Tajweed is on by default for mushaf pages, while the table's translation defaults to shown; an explicit `ayahTajweedOn` choice wins on every surface and `aayatun_mushaf_translation_v1` remembers the translation toggle. Controls are icon-only (`title` + `aria-label` + `aria-pressed`, Material `translate` SVG for translations) because the labels crowded narrow screens; the shared verse modal (`partials/_verse_modal.html`, also used by `/search`) is reused here. Both mushaf reading views (`/page/<n>` and `/mushaf/<surah>`) start their control row with the same zoom stepper (`partials/_mushaf_zoom.html`): circular −/+ buttons around a `NNN%` readout at 100/125/150/175 %, separated from the toggles by a hairline rule, disabled at the ends. `static/js/mushaf-zoom.js` stores the step index in `localStorage['aayatun_mushaf_zoom_v1']` (shared by both views) and writes `--mushaf-zoom`, which `static/css/style.css` multiplies into `.mushaf-ayah` (225 % plain, 165 % QCF), so the tables simply get larger text and reflow; the printed line layout is px-sized and refits through `MushafZoom.onChange`. The verse page's main control row (next to share/play) carries an icon-only **Mushaf** button that opens `/page/<qcf_page>?v=<surah>:<verse>`; it removes itself when `window.self !== window.top` so it cannot navigate the parent out of an open modal, and it hides while the More menu is open. On arrival the page centres that verse and paints a 4 s highlight (`.mushaf-row-jump` in table mode, `.mushaf-seg-jump` across every segment in layout mode). On the index page, choosing **Jump to → page** disables the surah picker and the whole-surah buttons (`#whole-surah-row.is-disabled`), since neither uses a surah. The layout view's credit line names zonetecde/mushaf-layout (ISC) and the King Fahd Complex glyphs. Above the mushaf (both table and layout) sits a collapsed **Page Overview 🤖** accordion with the generated `context`/`summary` paragraphs and the shared AI warning banner (`partials/_ai_notice.html`, also used by the verse page's AI Overview). It reuses the verse accordion's 90% text size and is borderless (base.html injects inline `.accordion` borders in dark mode, so `static/css/style.css` overrides the overview with `!important`). Swiping left/right anywhere outside the controls moves to the next/previous page (left = next, matching the verse carousel); `ArrowLeft`/`ArrowRight` turn the page the way the on-screen header arrows read (left = previous, right = next), ignoring modifiers, typing targets and an open modal. Swipe uses the same pointer-drag model as `verse-nav.js` (axis detection, pointer capture, `preventDefault`, follow-the-finger, 25 %/velocity commit) but tracks the finger 1:1 (no half-speed factor, only the last 15 % damped) and writes the transform once per animation frame, with `will-change: transform` applied only while `mushaf-swiping`; the commit slide is 110 ms and the rejected-swipe ease-back 120 ms. The route sets `Cache-Control: private, max-age=300` and the script prefetches the two neighbour pages (plus their QCF fonts when tajweed is on) 900 ms after load, so a turn is a cache hit. The listener starts on `document` but ignores links/buttons, the verse modal/dimmer and accordion headers, so vertical drags still scroll and taps still open verses. `body.mushaf-page-body` sets `touch-action: pan-y pinch-zoom` and `overscroll-behavior-x: none`, and a short slide/fade precedes navigation unless `prefers-reduced-motion`.
- `app.py` holds all routes (flat, no blueprints). `/theme/<theme_id>` (0–11) renders `theme.html` (extends `comprehensive.html`): every verse tagged with one AI-assisted theme in canonical mushaf order, as a flat DataTable like the surah pages — `S:V` ref cell with `data-order` = zero-padded `surah*1000+verse` (so the default col-0 sort stays mushaf order) plus the surah name below, `showModal` on the cell, QCF text and translation, zoom stepper, tajweed and translation toggles, icon-only controls. The header's prev/next arrows rotate through the 12 themes; the Merriweather theme-name title (no icon, no caret) is a button (`#theme-menu-btn`) that toggles a Fomantic `pointing popup` (`#theme-menu-popup`, anchored below the title): the twelve themes as menu items — colored dot + name, current one marked with `aria-current` and a bold `.active` style — a hairline `.theme-menu-divider`, then `<i class="left arrow icon"></i> Home Page`; the popup also hides on `pageshow` like the More Apps menu. Under the navbar sits a live `Showing X–Y of Z verses about “<Theme>”` line (`#theme-page-count`, updated on every DataTables draw, showing the filtered count and `(filtered from N)` when a search is active) — the static verse-count subtitle was removed. The theme name is shown only once, in the navbar title. The verse page's theme pill links to `/theme/<id>?v=<surah>:<verse>` (`window.AAYATUN_SURAH_THEMES`, kept in step on `aayatun:verse`); on arrival the page finds the row's position among `api.rows({order:'current', search:'applied'}).nodes()`, jumps the DataTable to that page, and paints a 4 s `.mushaf-row-jump` highlight on it (search filter cleared first if it excludes the verse). `library.get_theme_page(theme_id)` (`lru_cache(maxsize=12)`) builds everything from local files (Arabic, translation, `qcf_mem`); theme counts up to 1,702 rows (Judgment). Share is text-only (link with the count and `#aayatun`, no canvas card), wired through `data-theme`/`data-theme-count` in the `_share_macros.html` button. The page registers `pages.COMP_THEME = 7` for the index's continue-reading link.
- Verse pages ship only the current verse plus empty accordions. `GET /api/v1/verse/<s>/<v>` is the per-verse core payload (token-protected), `GET /api/v1/verse/<s>/<v>/<section>` renders one accordion section on demand, and `GET /api/v1/surah/<n>` returns the whole surah as compact `[[ayah, translation, page, codev2], …]` (no token, gzip, `no-store` so only the JS memory cache holds it). `library.get_surah_core` is `lru_cache(maxsize=4)` and reads only local DBs (`peek_qcf_ayah` never hits the network; the seed makes it always present).
- The verse-reference column (number on the surah/tafsir pages, `S:V` on the mushaf and theme pages) uses Lora 110% everywhere.
- JS-driven show/hide uses gentle fades (~150–180 ms) rather than instant display swaps: the translation rows on the Arabic/Theme/Mushaf table views, the mushaf page's table ↔ printed-line layout switch (opacity cross-fade; the lines view keeps its paint-driven `visibility` reveal and eases in at the same time), the verse page's control row and More menu (audio box, control buttons, band of circular buttons, tajweed legend strip), the modal's loading spinner, and the map lead-card's two-line translation and suggestion (cross-faded via `.is-fading` + `fadeSwap`).
- `static/js/verse-nav.js` keeps surah payloads in a memory-only LRU (3 entries) and drives the swipe carousel: two 3-pane tracks (ayah + translation), pointer drag with a 25 %/velocity commit, then `applyVerse()` + instant re-centre. No sessionStorage/IndexedDB/service-worker caching of the payload. It preloads the next/prev 3 page fonts.
- Offline verses: `verse-nav.js` writes every verse actually shown (max 60, LRU by timestamp) to `localStorage['aayatun_verse_offline_v1']` (Arabic, translation, QCF text/page, prev/next). `dataFor`/`loadVerse` fall back to it when the API is unreachable, and `static/offline.html` renders the saved verse when an uncached verse navigation fails offline. Do not grow this into a surah-payload cache.
- `templates/base.html` is the shared shell. `templates/comprehensive.html` extends it and is the layout for surah-wide pages (`translation`, `tafsir/*`, `mushaf`). All three keep DataTables pagination (`paging`/`stateSave`/`lengthChange` are `true`); the `{% if mushaf %}` blocks in that template now only choose the mushaf markup (`mushaf-ayah`, the hidden QCF span and the extra translation), not the table options. `{% block bismillah_row %}` is a display-only hook: the Arabic view supplies a `<template>` containing a real two-cell row, and DataTables' `drawCallback` clones it to the top of page one's `<tbody>` after each draw. This keeps the basmala under the search controls with the verse rows without making it sortable or part of pagination. Other surah-wide pages leave the block empty. Every page with a clickable verse-reference column carries a muted `.page-hint` line ("Click on the left column (verse) to open verse details for the corresponding verse." where the column shows the verse number — surah-wide views — and "surah:verse" where it shows S:V refs — mushaf, theme): the surah-wide views and the theme page render it inside their content_heading block, the mushaf page renders it directly under its subtitle.
- Sharing: `static/js/share.js` (loaded by `base.html`) is the only implementation. `templates/partials/_share_macros.html` renders the icon button on `/page`, `/mushaf`, `/translation`, `/tafsir/en` and `/tafsir/bn`; the verse page's own `#share-btn` calls `AayatunShare.shareVerse` with `state.ayah` (the plain Uthmani text, kept separately from the QCF codepoints the h1 may hold). Text formats: verse = surah `S:V`, blank line, translation, `Read on Aayatun: URL`, `#aayatun`; surah = `Surah Name (N) — <view label> on Aayatun.` + URL + tag; page = `Mushaf page N — range` + `Read on Aayatun: URL` + tag. The URL lives inside the text (no separate `url` field) so it cannot be dropped or duplicated. Order: `navigator.share` (with the card when one exists), then clipboard + checkmark, then `window.prompt`. There is no download fallback: without file sharing the text is shared/copied.
- Share cards: four surfaces get a PNG, and it is **drawn on a canvas**, never a screenshot (html2canvas was removed). `/<surah>/<verse>` → title + plain Arabic + the verse's translation. `/mushaf/<surah>` (arabic) and `/page/<n>` → title + **the first five verses (or the whole surah when it has fewer)** as one flowing Arabic paragraph with an ornate end-of-ayah medallion (`U+06DD` + Arabic-Indic digits) after each verse, then all the translations underneath as a second flowing paragraph in smaller muted text, with the same medallion inline after each verse so a translation can be paired with its Arabic. `/translation/<surah>` sets `card.skipArabic` and draws **only** the translation paragraph (same medallions), because the Arabic would double the card without adding anything to a translation share. When the view has more verses than the card shows, the drawn paragraph(s) end with a `…` (page 42, four verses, gets none; page 604 does). `/tafsir/*` stays text-only. The server renders those rows as `data-share-card='[[surah, verse, arabic, translation], …]'` on the button (single-quoted attribute, Flask `tojson` escapes the quotes), because `/translation` paginates its DataTables rows and carries no Arabic in the DOM, and sets `data-share-more="1"` when truncated (routes pass `share_card`/`share_more`, the macro takes `card=`/`more=`); `payloadFromButton` parses them into `payload.verses`/`payload.more` and `cardFor` copies them to `card.verses`/`card.more`. The translation paragraph is wrapped as tokens — words measured in Open Sans, medallions (`verseMarker()`, ~1.5× the translation size) in Scheherazade — and a medallion never starts a line: it may overhang the previous line by its own width instead. The title is Merriweather (`#4183C4`, `#9CC4FF` in dark) and reads `Al-Baqarah 2:255`, `Al-Baqarah (2)` or `Mushaf page 42`; a muted subtitle carries the view (`Arabic text with translation`, `English translation`) or the page's verse range. Arabic for the single-verse card is always `state.ayah`; the multi-verse cards use the server's plain Uthmani rows, never `code_v2`, so a card is never coloured. Reading cards are laid out at 420 px and rendered at 1080 px wide (the map card is a 460×818 layout rendered at 1080×1920), 26 px padding, word-wrapped by hand (`measureText`, `ctx.direction='rtl'` for the Arabic — bidi orders a pure-Arabic run correctly either way). The verse card grows with its text (316 px minimum body, so a short verse still fills a square, Arabic 38 px, translation 17 px); the multi-verse card starts at 31/15 px Arabic/translation and shrinks both (to 21/12 px) until the body fits 1320 CSS px, so five long verses stay readable without a 3000 px strip. Band: `aayatun.com` + the full URL, shrunk to fit. `document.fonts.load()` warms Merriweather/Scheherazade/Open Sans at load, with an Arabic sample, because Google Fonts ships Scheherazade as unicode-range subsets: a bare load() only fetched the Latin subset, which left the `/translation` card (no Arabic on the page) drawing tofu boxes. Drawing is synchronous (`toDataURL` → `atob` → `File`), so the whole thing stays inside the tap and Safari keeps its user activation; there is no warm-up cache, no scroll/resize listener and no `registerVerse`.
- `base.html` owns the default OG/Twitter meta (`og:site_name/type/title/description/url/image`, `twitter:card=summary`). The reading templates override `og_title`/`og_description`; the verse page also sets `og_type=article` and `meta_description`. `twitter:*` reuses `self.og_*()`, so override those blocks rather than writing raw tags.
- The index's **Surprise me!** button uses `surpriseTarget()`: 50% opens a random `/page/<1..604>`, otherwise the server-picked random ruku verse (`rand_surah`, unchanged). The branch is chosen in the browser with `Math.random()`, so the page response stays cacheable.
- The index content is top-aligned (`.ui.basic.segment { justify-content: flex-start; padding-top: clamp(12px, 4vh, 48px) }`) rather than vertically centered, `body`'s global `margin-bottom: 60px` is overridden to 0 on the page, and the flex wrapper keeps `min-height: 100dvh` (growing only with real content), so the footer (v2.0 / Dark Theme / More Apps) sits inside the first viewport on large screens. Recently Read is a one-line horizontal scroll strip (`#recent-list`, `nowrap`, chips never wrap); on pointer devices it shows a thin scrollbar (webkit + `scrollbar-width: thin`), hidden on coarse pointers (`@media (hover: none) and (pointer: coarse)`). The footer line (v2.0 / Dark Theme / More Apps) is pinned to the viewport bottom as `.app-footer-bar` (fixed, translucent like the loading bar — rgba(255,255,255,.85) / rgba(28,29,30,.85), safe-area padding, z-index 1050) with a matching `.app-footer-spacer` keeping in-flow content clear of it; `#more-apps-popup` stays a sibling of the bar, not a child, so its fixed positioning and the JS `place()` anchoring to `#more-apps-btn` are unaffected. The stray `<br>` before `{% block content2 %}` in `base.html` is gone.
- `prayer-time.html` and `daily-counter.html` at the repo root are standalone (no Jinja, no base) and served verbatim at `/prayer-time` and `/daily-counter` (the counter is branded **Habit Tracker** in the UI and manifests; filenames, the route, the `daily-counter-v1` storage key and the manifest filename stay). The toolbar carries an import/export button beside the install button: a dialog copies the raw `daily-counter-v1` array to the clipboard (export) and imports a pasted backup — dry-run summary with explicit confirm, per-date overwrite merge, match by id then case-insensitive name, one-level `daily-counter-v1-bak` snapshot with an Undo toast via `send_from_directory('.', …)`, so they must stay at the root. Prayer Time's "See details" iframe loads `https://www.aayatun.com/<surah>/<verse>` unless the page is already on `aayatun.com`. The index footer links both pages through the **More Apps** pointing popup (`#more-apps-popup`, a custom fixed-position popover toggled by `#more-apps-btn`, not a modal — Fomantic's popup opens on touchstart, so the synthesized click landed on the just-opened popup and its clickaway closed it again, which never let the menu open on phone), the trigger is a plain `<a href="#" id="more-apps-btn" class="footer-link" role="button" tabindex="0">` (tap = click toggle; mousedown outside and Escape close it), and the "Aayatun v2.0" label links to `https://github.com/OnixHoque/aayatun/tree/deploy`. Each standalone page links its **own** manifest (`/static/manifest-prayer.json`, `/static/manifest-counter.json`) so installing from it opens that page rather than the Aayatun index, and both carry a `[data-install-app]` button wired by `static/js/install.js` (real `beforeinstallprompt` sheet on Chromium, a Share → Add to Home Screen help sheet on iOS, hidden in standalone/in-app browsers).
- Per-request network: alquran.cloud (tajweed markup) and quran.com (QCF `code_v2` + per-page COLRv1 fonts). Calls use short timeouts, sqlite caches, background warmers, and a plain-text fallback, so pages must still work when those APIs are down.
- `/font/v4/<page>.woff2` serves page fonts (1–604) with immutable caching and downloads them into `db/fonts/` on first use.

## Quiz

- `/quiz/stats` renders `templates/quiz_stats.html` — a read-only server-rendered tally of the bank: total questions, verses covered, difficulty bar (easy/medium/hard), per-aspect counts, skip breakdown (basmala/muqatta'at/≤3-word/other) and generation models/dates via `library.quiz_bank_stats()`. Linked from the bottom of the quiz start screen.
- Sessions come from `POST /api/v1/quiz/session` (token-protected like the verse API, `private, no-store`). The body carries `{seen: [...], explored: <base64 b64c6236-bit bitset>, done: <base64 6236-bit bitset>, ids: [...]}`. Selection order: (A) verses explored on the map but not yet quizzed → (B) unexplored + unquizzed → (C) explored + already quizzed → (D) unexplored + already quizzed (only once everything else is exhausted). The client rebuilds both bitsets from localStorage each request (`aayatun_read_map_v2` for explored, `aayatun_quiz_done_v1` for attended). When `ids` is present the server serves exactly those questions (bypassing seen-exclusion and tiers) — used by the per-verse Retake button on the 5 most recent history rows (served-order `qids` stored in the history entry, choices reshuffled, deterministic set). Every question now carries a stable `id` (`surah:verse:aspect:prompt-md5`). `library.get_random_session(exclude=..., explored=..., done=..., retake_ids=...)` picks the verse, filters seen questions when ≥5 unseen remain, skips the tier if rethinking, and inlines the verse `index` in the payload. Attendance (`aayatun_quiz_done_v1`) is marked when a round completes (answered or timed out) and wiped by the quiz "Clear" and the map's Delete history button. `quiz_session_count()` feeds the Verses stat.
- `/quiz` renders `templates/quiz.html` (extends `base.html`, versedetails geometry via `block content`): start screen (best score, attempt count, history list with per-row Retake link + clear-confirm modal, shared AI notice, "Verses" stat = number of verses with a complete session bank), 5-question rounds — each **session is a single verse** (translation / word_meaning / grammar / tafsir / ai_context, each 30 s, aspect pill + difficulty, hint, dots progress bar, reference shown from the start, RTL Arabic verse card, feedback popup with two one-use-per-session lifelines (+30s scales the timer bar to the live window; 50/50 removes two wrong choices), popup animates in with dim/spring/icon-pop/stagger; wrong pick shakes, correct pick pulses; dimmed overlay without backdrop blur; advances only via Next) — and a result screen (percentage ring, per-question review with aspect labels, share button). `static/js/quiz.js` drives it end to end; `static/css/quiz.css` carries the styles. The seen list lives in `localStorage['aayatun_quiz_seen_v1']` (cap 2,000, last 400 sent). The client shows the verse reference from the start and labels each question with its aspect pill.
- The bank is `db/verse_quizzes.db` — tracked SQLite table `verse_quizzes(surah, verse, questions JSON, count, skipped_reason, model, generated_at)`, one row per verse. The target shape is **18 questions per verse** (≈ 100K total): English only, aspects translation/word_meaning/grammar/tafsir/ai_context (4/4/4/3/3 per verse, rotation keeps the bank-wide share equal), difficulty **9 easy / 7 medium / 2 hard** (bank-wide 50/40/10). Generated offline by `/mnt/d/PROJECTS/aayatun_ai_content/generate_verse_quizzes.py` (OpenAI `gpt-5.6-sol`, fallback `gpt-4o-mini`; resumable, `--force` regenerates stored rows; validation enforces exactly 18 questions per verse with aspect counts 3–4, difficulty within tolerance ±2, unique choices, hint without the answer, no all/none-of-the-above, no duplicate prompts). A verse is only skipped when its Ibn Kathir excerpt or the AI verse-analysis note is missing/too thin (stored `count = 0` + `skipped_reason`, never fabricated). The pilot set (16 verses, 80 questions) is committed; the remainder is generated by a resumable background job. `get_random_session()` serves a random 5 of however many the verse carries (≥ 5), aspect order preserved. Enriched rows may coexist with older 5-question rows in the same bank. English only.
- Score history lives only in `localStorage['aayatun_quiz_history_v1']` (max 20 entries, newest first, `{score, total, date, durationSec, difficulties[], aspects[], hints[], correct[], points}`); best/attempts shown on the start screen, cleared via the confirmation modal; the history list shows the latest five attempts with a "Show more / Show less" toggle for the rest; the five dots per attempt are full blue = correct, hollow blue = missed, yellow = hint used. The quiz page fades each view in (~180 ms translate+opacity, respects `prefers-reduced-motion`). No server-side storage.
- Scoring: 200 points per correct answer, session total shown as a star chip in the topbar's left cell (five dots stay centered, timer flush right in the same row) during round and result; correct answers arc animated "+200" tokens from the tapped choice into the chip (Web Animations API), the chip bumps, and the counter count-up-ticks to the new total; `prefers-reduced-motion` skips the flight. The result screen shows the session points under the ring (`N points this session · max 1,000`), and the total is stored in the history entry.
- Sharing: `AayatunShare.shareQuiz({score, total}, btn)` draws a `quiz` canvas card (`drawQuizCard` in `share.js`: kicker + Merriweather title, colour-coded score ring, date, `N questions · 30 seconds each`, brand band with `/quiz`). Text fallback: "I scored N/5 on the Aayatun Quran Quiz. Can you beat me?" + URL + `#aayatun`.
- The index's More Apps popup (`#more-apps-popup`) carries the Quran Quiz as its first item (graduation-cap icon, `url_for('quiz')`); the home-actions-row is back to Surprise me! / Quran Exploration Map, two columns. `quiz.css`, `quiz.js` and `/quiz` are in the service worker's `CORE_ASSETS`; bump `CACHE_NAME` when changing them (currently v146).
- Verse details (`/<surah>/<verse>`) render an (initially hidden) icon-only graduation-cap button (`#verse-quiz-btn`) in the control row; the 6,236-bit base64 `window.AAYATUN_QUIZ_BANK` (780 bytes) decides visibility on load and after every `aayatun:verse` swipe — looked up by the canonical mushaf verse index from `AAYATUN_SURAH_STARTS + verse - 1`, so it works across surah boundaries too. The button appears exactly for verses with a bank; hidden inside the shared verse-modal iframe (`self !== top` → remove). Clicking navigates via `AayatunNav.go('/quiz?verse=S:V')`; `/quiz` reads the param, and when the bank exists the server serves that verse's questions directly (`forced_verse` in `get_random_session`, seen-exclusion and tiers bypassed, answers shuffled, set deterministic); a missing verse falls back to a random session with a muted note. The button fades with the others when the More menu opens.


## Frontend gotchas

- Verse-page tajweed: the head script adds `html.tajweed-pending` (hides the server-rendered plain `h1`), and the parse-time script after the controls applies the colored rendering then calls `reveal()`. Keep that init parse-time; moving it back into `DOMContentLoaded` brings back the plain→tajweed flash. **The parse-time script must never reference jQuery** — jQuery is loaded deferred, so a `jQuery`/`$` call there throws and `reveal()` never runs, leaving the verse invisible (this exact failure shipped once via `markStrip`). `VerseTajweed.renderInto(el, data)` paints any carousel pane (per-page `@font-palette-values`, fonts preloaded with `preloadPage`); the carousel keeps the only `id="ayah"` on the current pane, and neighbour panes are `div.ayah-text` (one `h1` per page).
- The navigation loading bar in `base.html` keeps `showLoading`/`hideLoading` outside jQuery/`DOMContentLoaded` and passes state across pages via `sessionStorage['aayatun_loading']` + `html.is-loading`; iOS Chrome needs this path. Every navigation path must trigger it: links are caught by the capture-phase click listener, forms by the `submit` listener (search), and buttons/JS redirects either call `AayatunNav.go(url[, replace])` (which also shows the **parent** page's bar when called from the verse-modal iframe) or carry `data-loading`/`data-navigate` (+ optional `data-href`). A button whose inline `onclick` assigns `location.href`/`replace`/`assign` is also caught as a safety net. Don't add a new `location.href = …` button handler without one of those hooks, or the bar silently skips it (this was the **Surprise me!** bug).
- `static/service-worker.js` precaches the app shell (including `/map`) and is registered only from `index.html` (the standalone pages register the same worker); bump `CACHE_NAME` when changing precached assets or caching logic. `CORE_ASSETS` also holds the three manifests, `install.js` and the Material Symbols stylesheet used by Prayer Time's sunrise/sunset pills; `install` then fetches that CSS, extracts its `url(https:…)` glyph files and caches them, so the icons render offline too. Every `respondWith` path must resolve to a `Response`: a failed fetch with nothing cached used to resolve `undefined` and throw "Failed to convert value to 'Response'", so the SWR/cache-first paths fall back to a 504 `networkError()` and navigations to `offline.html` then an inline 503 page.
- Mushaf layout view (`templates/mushaf_page.html`): its JS runs from the base page's `DOMContentLoaded` block, so `QcfFont` is already defined. It keeps the view `visibility: hidden` until the active face is painted (QCF if tajweed is on, plain Scheherazade otherwise) and the lines are fitted (measure at 100 px, scale the widest line to the column, re-fit on resize, on every tajweed toggle and on every zoom step). Each segment holds both a `.mushaf-plain` and a `.mushaf-qcf` span, and only the visible one is measured, so the hidden face cannot stretch a line. Pages 1–2 additionally cap that size at `100 × avail ÷ 1640` because their printed lines are much shorter than a normal page's, which otherwise made their text ~20 % larger than the rest of the mushaf. Only lines flagged `endblock` (last line of a surah or of the page) may stay short; every other line is justified, which is why mid-verse line breaks must not be right-aligned. At zoom > 100 % the font grows but the line box stays the column width, so a printed line wraps onto the next visual line (justified, with its last fragment right-aligned) instead of overflowing sideways; at 100 % the lines still fit exactly and keep `white-space: nowrap`, so a rounding pixel cannot break them. A verse split across lines shares one `data-surah`/`data-verse`, and the hover/focus handler toggles `.mushaf-seg-active` on every segment of it; the highlight is transient (cleared on leave/click, never stored). Because the glyph line box is tall (line-height 1.75), the highlight is a centred gradient band (`background-size: 100% 55%`) rather than a full-height background, so it does not bleed into the neighbouring lines. The 100 px measuring pass needs `.mushaf-layout { overflow: hidden }` or it flashes a horizontal scrollbar.
- The shared verse modal (`partials/_verse_modal.html`) reveals on the iframe's `DOMContentLoaded` (polled, 40 ms) instead of `load`, and the verse page's two `<audio>` tags use `preload="none"`, so opening a modal downloads no MP3s. Don't move back to `load` or `preload="auto"` without measuring: it added ~600 ms and two external requests per open. Hiding the modal (close icon, ESC, or `.modal('hide')`) pauses and rewinds every `<audio>` inside the iframe via the modal's `onHide`; the iframe keeps playing otherwise.
- **Recently Read** on the index is fed by `static/js/recent.js`, which records the three reading views through their server-rendered `<meta name="aayatun-read" content="type|key|label">` (`verse` = `/<s>/<v>`, `page` = `/page/<n>`, `mushaf` = `/mushaf/<surah>`). Entries live in `localStorage['aayatun_recent_reads_v1']` (max 5, newest first); revisiting a URL moves it to the front, and a run of the same kind collapses to its newest entry, so 42 → 43 → 44 leaves only "Page 44". Pages without the meta (home, search, translation, tafsir, prayer-time) never record, and a verse page opened inside the shared modal iframe keeps the chips unchanged. The index renders the chips with `createElement`/`textContent`; clearing now lives on the map page (`/map`) and calls `AayatunRecent.clearAll()`.
- **Quran Exploration Map** (`static/js/reading-map.js`, served at `/map`): the **Quran Exploration Map** button on the index sits beside **Surprise me!** in a two-column `.home-actions-row` (plain `ui basic fluid button`s, compact padding so they stay the same height as the Go button; below 560 px the row becomes one full-width column so neither label wraps) and navigates to the standalone map page via `AayatunNav.go('/map')`. The page (`templates/map.html`, `app.py: reading_map`, hidden `#surah` select for the surah names/counts; `.ui text container` stays empty so the page sits in a full-width `.ui container` like the search page) renders one square per verse in canonical mushaf order (6,236 squares, GitHub-contribution style) — contents are identical to what used to be a modal on the index. The row is always visible, independent of whether Recently Read has chips. Swiping inside `verse-nav.js` never reloads, so `applyVerse()` dispatches `aayatun:verse`; `recent.js` maps that position through `window.AAYATUN_SURAH_STARTS` (rendered on verse pages from `library.surah_starts()`) and bumps the level and the verse chip.
